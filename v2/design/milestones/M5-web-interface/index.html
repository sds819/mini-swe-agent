    M5 — Web 版

    目标：把 coding agent 从「终端里的一个程序」搬到浏览器里，并让模型参数可以在网页上配。 依赖：M0–M4 全部完成。本里程碑不改核心架构，只加一层新的交互面。 状态：已完成。代码已落地，测试与使用文档已补齐。 配套：M5-web-modules.md 讲模块与函数级别的设计（本文讲总体设计）。

    1. 功能范围

    编号 功能 优先级 说明
    F5.1 模型配置页 P0 /settings，显式字段 + 自由 kwargs，含分层来源预览与连通性测试
    F5.2 聊天页 P0 /，跑 agent、流式输出、工具卡、diff 预览
    F5.3 事件流 P0 SSE 推送；环形缓冲 + since 断线续传
    F5.4 工具审批 P0 浏览器点 Allow / Deny / Always；超时自动 DENY
    F5.5 会话管理 P1 列表 / 续接 / fork / 回放
    F5.6 文件浏览与 diff P1 目录树、读文件、工作区 diff
    F5.7 Slash 命令 P1 复用 ui/commands 的 25 个内置命令与自定义命令
    F5.8 中断 P1 /interrupt 停掉正在跑的一轮

    2. 总体分层与边界

    2.1 为什么不用改核心

    web 版需要的四件事，核心里已经有了，所以本里程碑一行核心逻辑都不重写：

    需要的能力 现成的地基
    模型参数可结构化读写 pydantic ModelConfig（config/schema.py:38），model_kwargs 直传 litellm.completion
    配置分层 config/loader.py 的四层合并（defaults < 项目 < 用户 < CLI）
    事件可订阅 core/events.py:65 的 EventBus，同步发布/订阅，TUI 已是它的一个订阅者
    回合可放到别的线程 核心全程同步，ui/tui.py:267 已经在工作线程里跑 turn

    所以 web 版 = 一个 FastAPI 应用 + 每会话一个工作线程 + SSE 把事件推给浏览器， 外加复用现有的工具、diff、checkpoint、slash 命令。

    2.2 模块布局

    src/coderagent/web/
├── __init__.py      # 只有 docstring。绝不在这里 import fastapi
├── app.py           # create_app(config, cwd, ...) -> FastAPI
├── api.py           # APIRouter(prefix="/api")：全部 REST + SSE 端点
├── sessions.py      # SessionRegistry + SessionRuntime：线程、环形缓冲、turn 执行
├── events.py        # normalize(Event) -> list[item]：核心事件 → 前端条目
├── approver.py      # WebApprover：阻塞式审批，答案由 HTTP 送回
├── config_api.py    # 读写 ~/.coderagent/config.yaml、分层预览、脱敏、连通性测试
├── files.py         # 文件浏览：越界检查、列目录、读文件、diff
├── i18n.py          # 页面语言：STRINGS、LANGUAGES、地区判断与 cookie
├── server.py        # serve(cwd, host, port)：uvicorn 入口
├── templates/       # en/ 与 zh/ 两套模板（每套 base/chat/settings/macros.html）
└── static/          # app.css / app.js（原生 JS，无构建步骤）

    web/__init__.py 只放 docstring：from coderagent.web.server import serve 在 ui/cli.py 的 web 子命令里惰性导入（照抄 coder export 的写法，ui/cli.py:160）。 这样 fastapi 永远不是硬依赖——没装 web extra 的人 import coderagent 不受影响。

    3. 会话运行时

    3.1 线程模型

    turn 线程                          事件循环
──────────                         ─────────
loop.run_turn()                   SSE 生成器 await queue.get()
  bus.publish(Event) ──► 订阅者（turn 线程）
                            │
                            ▼
                     normalize(event) → item
                            ▼
                     runtime.emit(item)
                       ├─ 环形缓冲 deque(maxlen=1000) 追加 {"seq":n, ...}
                       │    （瞬时条目例外：流式的增量只推给订阅者，不留）
                       └─ 每个订阅者：loop.call_soon_threadsafe(queue.put_nowait, item)
    • 每会话一个 worker 线程，queue.Queue 收活；turn 期间持 busy 标志。
    • FastAPI 事件循环里绝不跑 agent 代码：碰文件系统/模型/loop 的端点都写成普通 def （Starlette 丢线程池），或直接交给会话 worker。
    • build_loop（run.py:105）每会话建一次并缓存：它会起 MCP server 线程（run.py:125） 且会往全局命令表追加（run.py:132），不能每请求建。
    • 事件订阅要逐个 EventType 注册（EventBus 没有通配订阅，core/events.py:71）： for t in EventType: bus.subscribe(t, handler)。
    • loop.cancel = runtime.cancel.is_set，每轮前赋值（照 ui/tui.py:273）。

    3.2 缓冲与回放

    SessionRuntime._replay() 在构造时把事件日志过一遍 normalize() 灌进环形缓冲。 于是 /items?since=0 与 SSE 流共用一个 seq 空间：

    • 浏览器打开页面 → 拉 /items?since=0（拿到历史）→ 打开 /stream?since=<seq>（拿增量）。
    • 断线重连 → 带 since=<seq> → attach() 把缓冲里 seq > since 的塞进队列。
    • 流式的增量（text_delta / reasoning_delta）是瞬时的：它们有 seq（顺序不变）， 但不进缓冲。晚到的浏览器看不到它们，但能看到随后那条完整的 assistant_message。

    3.3 一个会话一次只有一个 turn

    SessionStore.append 本身没有锁（core/session.py:81），所以并发写会串。 SessionRuntime.submit() 在 busy 已置位时抛 SessionBusy → /messages 返回 409。

    3.4 会话换 id 的问题

    /clear、/resume 会换 session id（ui/commands/builtin.py:98、:111 调 loop.switch_to）。 浏览器还在往旧 id 推流，所以 SessionRegistry 必须 re-key：

    def rekey(self, runtime, old_id, new_id):
    self._runtimes.pop(old_id, None)
    self._runtimes[new_id] = runtime

    运行时同时发一条 session_switched 条目，前端据此换订阅目标。

    4. 事件到条目的翻译

    核心说的是事件，浏览器说的是条目。web/events.py 的 normalize(event) -> list[dict] 是唯一的翻译层。

    核心事件 条目 kind 备注
    USER_MESSAGE user_message
    ASSISTANT_MESSAGE assistant_message reasoning 可折叠，受 config.ui.show_reasoning 控制
    TEXT_DELTA text_delta 不入日志，只在事件总线上（core/events.py:15）；也不进环形缓冲（瞬时，见 §17.1）
    REASONING reasoning_delta 同上
    TOOL_CALL tool_call 一条动作一个条目；标题用 ui/widgets/tool_card.py:11 的 summarize(args)
    TOOL_RESULT tool_result 两种 payload，见下
    APPROVAL_REQUEST approval_request 带 id/tool/params/reason
    APPROVAL_RESPONSE approval_response 带 timed_out
    STATE_CHANGE state
    COMPACTION / REFLECTION / REVERTED compaction / reflection / reverted 分隔线
    VERIFY verify 验证命令的结果
    ERROR error 红条

    4.1 TOOL_RESULT 的两种形状

    来源 payload 含义
    执行器（tools/executor.py:181） {"tool": ..., "tool_call_id": ..., "content": ..., "diff": ...} 知道是哪个工具、还带 diff
    上下文（core/context.py:136） {"messages": [ ... ]} 记录模型实际看到的观察值

    normalize() 必须区分："tool" in payload 才是执行器那一版。前端按 tool_call_id 更新同一张卡，不重复渲染。

    4.2 diff 的持久化

    执行器那一版原本只发不存，回放就看不到 diff。改 tools/executor.py 让它也 store.append 进事件日志：

    ctx.bus.publish(event)
if self.store is not None:
    """The log keeps the result, so that the replay shows the diff of the change."""
    self.store.append(ctx.session.id, event)

    副作用：事件日志里 TOOL_RESULT 出现两次（执行器一次、上下文一次）。 core/context.py:87 的 restore() 不受影响（它读 payload["messages"]，执行器变体没这个键）。 tests/coderagent/test_loop.py 的事件序列断言要跟着改。

    5. 传输：SSE + REST

    方向 机制 为什么
    服务端 → 浏览器 SSE（text/event-stream） 单向推送、自带重连、不需要额外协议
    浏览器 → 服务端 REST（JSON） 审批/命令/配置都是「一次请求一次回答」

    不用 WebSocket：没有双向的实时需求，SSE 的重连与心跳是现成的。

    SSE 帧格式：data: {json}\n\n，每 15 秒一个 : keep-alive\n\n。 一轮结束时发 turn_end，流随之关闭；浏览器拿新的 since 重开。

    6. 审批

    agent 线程                          浏览器
──────────                          ───────
executor._prepare()
  policy.evaluate → "ask"
  approver.request(tool, params, reason)
    bus.publish(APPROVAL_REQUEST) ──► SSE ──► 渲染审批卡
    event.wait(timeout)  ⏸               │
                                         │ 用户点 Allow/Deny/Always
    event.set()  ⏵ ◄── POST /api/approvals/{id} ──┘
  继续执行 / 拒绝
    • WebApprover（web/approver.py）在 worker 线程上阻塞，threading.Event 唤醒。
    • 超时自动 DENY（与 ui/tui.py:58 一致），默认 300 秒，超时再发一条 approval_response{timed_out:true} 让前端解释原因。
    • 未知/过期 id → 404。
    • Always allow 会往用户规则文件 ~/.coderagent/rules.yaml 写一条规则 （tools/executor.py:143 → tools/rules.py:118 add_rule）。UI 必须明确提示这一点。
    • Deny → 模型收到「用户拒绝」（tools/executor.py:126），模型会改口而不是硬改。

    7. Slash 命令

    原样复用 ui/commands/__init__.py:82 的 run(context, line)——25 个内置命令和自定义命令 都只通过 context.say(...) 说话，零 textual 依赖。

    • CommandContext.output 接到 runtime.emit({"kind": "command_output", "text": ...})。
    • 命令在会话 worker 线程里跑（/compact 会触发一次模型调用，/rewind 碰文件系统）。
    • 命令换 session id 时，registry 重新 key（见 §3.4）。

    7.1 register() 必须去重

    ui/commands/__init__.py:56 的 register() 原本无条件 append。web 是每会话一个 loop， 每建一次 loop 就注册一遍项目自定义命令 → 全局命令表无限膨胀、/help 出现重复。 改成按名字去重（同名替换）。

    8. 模型配置页

    8.1 显式字段

    字段 落点 说明
    model_name model.model_name 如 deepseek/deepseek-flash
    api_base model.model_kwargs.api_base 显式字段，因为它直通 litellm
    api_key model.model_kwargs.api_key 密码框；服务端只回 api_key_set + 掩码 hint
    max_retries model.max_retries 死配置，接线见 §8.4
    set_cache_control model.set_cache_control default_end / 空（mini 只认这两个）
    litellm_config model.litellm_config 别名文件；里面的别名可以当模型名用
    routing model.routing {purpose: model}
    routing_rules model.routing_rules {when, purpose} 行
    附加 kwargs model.model_kwargs 其余 自由 YAML/JSON 编辑框

    8.2 分层预览

    GET /api/config 返回 sources: {"model_name": "user", "api_base": "project", ...}， 按优先级 defaults < project < user 逐层看，最后一个定义了该 key 的层说了算； 环境变量只在没有任何层定义时兜底（目前只有 model_name 与 api_key 走这条路， 层名报 env）。

    8.3 写入

    只写 config_home()/"config.yaml"（paths.py:7），项目级 .coderagent/config.yaml 永不写 （它会进 git）。读现有 YAML → 只改 model: 下用户提交的子键 → yaml.safe_dump(sort_keys=False) 写回。未知顶层段（agent:/tools:/mcp:…）与未知 model: 子键原样保留。

    已知代价：注释会丢（不引 ruamel）。

    api_key 语义：省略/null → 保留原值；非空字符串 → 替换；"" → 删除。

    改完不热更新：运行中的 server 保留启动时的 Config；新会话建 loop 时重新 load_config() 生效（web/sessions.py 的 SessionRegistry.create()）。页面要提示 「新配置对新会话生效，当前会话用 /model <name> 切换」。

    8.4 max_retries 的接线

    mini 的 retry 次数来自 $MSWEA_MODEL_RETRY_STOP_AFTER_ATTEMPT （minisweagent/models/utils/retry.py:21），不是 model.max_retries。 在 web/server.py 建模型前把这个环境变量设成 model.max_retries，一行解决； 否则表单里就是个摆设。

    8.5 权限设置

    权限分两层，作用不同：

    层 改什么 生效时机
    设置页 用户级配置文件的 permissions: 段 新会话
    聊天页检查器 当前会话的 PermissionPolicy 立刻

    写：web/config_api.py 的 write_user_permissions()，和 write_user_model() 同构—— 只写用户级文件，只改 permissions.mode / deny_paths / include_dirs， permissions.rules 原样保留（规则是审批卡片上 Always allow 按钮写的，不是页面的事）。

    读：permissions_view(cwd, server_mode=...) 给出 mode / modes / deny_paths / include_dirs / source / server_mode。source 按 config_layers() 逐层判断每个字段来自哪一层， 和 §8.2 的 sources() 同一套办法。

    运行中切换：SessionRuntime.set_mode() 原地改 loop.executor.policy.mode 和 loop.session.permission_mode——和 /mode 命令完全相同的两行。策略是执行器问的那个对象， 所以下一个工具调用就能看到；ContextEngine 拿的是同一个策略对象，<permission_mode> 提示会自动跟着变，不用重建上下文。loop 还没建时只记下模式，build_loop() 用它。

    --permission-mode 盖过文件：build_policy() 是 permission_mode or config.permissions.mode （run.py:60）。服务器带模式启动时，配置文件里的 permissions.mode 是死的——页面要如实说， 不能让用户以为改了生效了（server_mode 非空时 source["mode"] 报 server）。

    一个坑：status() 在 loop 还没建时返回的是会话自己记下的模式（mode() 读 self._permission_mode，再回落 config.permissions.mode），不是启动时的配置值。

    不做的：浏览器里编辑 rules.yaml；把权限写进项目级 .coderagent/config.yaml（会进 git）。

    9. 文件浏览与 diff

    功能 复用
    列目录 tools/builtin/search.py 的 LsTool（遍历逻辑抽成公开的 list_entries(target, depth)）
    读文件 tools/builtin/fs.py 的 ReadTool（自带行号与截断）
    搜索 GlobTool/GrepTool（纯 Python，不依赖 rg）
    写操作预览 diff ui/widgets/diff_view.py:31 prospective_diff(tool, params, cwd)
    统一 diff 渲染 ui/widgets/diff_view.py:9 make_diff
    工作区 diff git diff -- <path>（web/files.py:79）；/diff 命令用的是 git diff --stat（ui/commands/builtin.py:142）

    9.1 路径安全三层

    Path.resolve()  →  边界检查（必须在 cwd 或 permissions.include_dirs 里）  →  工具自身的 resolve_path

    越界 → 403，文案沿用 tools/permissions.py:235 的写法。

    不能用 policy.evaluate("read", ...) 当边界检查——evaluate 走的是规则， 而规则不能放宽边界（tools/permissions.py:223-233 的 within_bounds 写着 「The rules of the user cannot widen this」）。但 evaluate 的语义是「这条调用 允不允许」，不是「这个路径在不在范围内」，用它当边界检查会把 「规则放行」和「路径越界」两件事混在一起。必须直接用边界检查。

    所以 tools/permissions.py 的边界检查是公开的 within_bounds(path) -> bool， web 直接复用，不重写路径安全逻辑。

    17. 实现说明（与原设计的偏差）

    • 没有用 X-Coder-Client 做浏览器的写请求鉴权之外的东西。所有写接口（消息、审批、 中断、配置写入、配置测试）都要这个头，读接口不要。这样 curl 照常能用， 跨站浏览器发不了。
    • SSE 的结束条件：一轮结束时发 turn_end（命令是 command_end），流随之关闭， 浏览器拿新的 since 重开。不用「空闲多久就关」的启发式——那会让「一轮里长时间没输出」 的情况提前断流。结束条件不再看 busy：turn_end 是在 busy 清掉之前发的， 用 busy 当条件会有竞态，流可能永远不关。
    • 命令也发 command_end：命令跑完发一条 {"kind": "command_end"}，前端与后端同一套 「这一轮结束了」的信号。
    • 每会话的 loop 懒建（第一次跑 turn 时才 build_loop），避免光看一眼会话列表就起一整套 MCP 线程。
    • 命令的输出走 command_output 条目，不混进对话气泡——命令不是模型说的话。

    17.1 实跑记录（DeepSeek，2026-11-08）

    真跑了一轮（coder web --cwd /tmp/webtest --port 8799），把踩到的写在这里：

    • text_delta 是逐 token 的，一轮「say hi」就有 14 条 text_delta。前端按 seq 追加到当前气泡是对的，但缓冲区会被 token 吃满：1000 条的环形缓冲，一轮长回答就 够把前面的历史挤掉。→ 已修（Q7）：流式的增量是瞬时条目，只推给正在听的浏览器， 不进环形缓冲（web/events.py 的 TRANSIENT_KINDS）；整段答案随后以一条 assistant_message 进缓冲。
    • 环境的 API key 现在也在设置页里：早期版本只读配置文件，所以 DEEPSEEK_API_KEY 这类 环境变量在页面上看不到（api_key_set 是 false），而 agent 其实在用它。已修：key 的来源 顺序是「配置 > 别名文件 > 厂商的环境变量」，sources.api_key 会报出它来自哪一层。
    • sources.model_name 显示 env：MSWEA_MODEL_NAME 在环境里时，模型名来自环境而不是 文件。这与 loader 的口径一致（文件 > 环境 > 默认）。
    • 每轮结束有一条 reflection 分隔线：那是 settle() 沉淀记忆的那次调用，它的钱算进 session_cost（实测一轮 0.00032，会话总额 0.00050）。
    • /help 的输出很长，一条 command_output 里塞了 25 行命令。前端要能折叠长输出。

    待办（Q7）：~~text_delta 逐 token 进缓冲，长回答会把历史挤出缓冲。~~ 已修：瞬时条目（text_delta / reasoning_delta）不进环形缓冲，只推给正在听的浏览器； 整段答案以 assistant_message 进缓冲。前端收到 assistant_message 时替换流式气泡 的内容，而不是再画一个气泡（原来会重复显示两遍）。
